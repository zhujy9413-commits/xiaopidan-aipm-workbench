# 范围判断与交付标准

## 1. 验证背景

简要说明任务场景、目标用户、触发场景、核心问题、现有替代办法、证据与约束。新产品关注核心价值是否成立；新功能关注它是否改善现有任务；改版关注明确的体验或效果问题；增长实验关注可归因的漏斗变化。不能将某个业务案例的指标口径当作所有项目的统一标准。

主要假设应能被结果支持或否定，说明“哪类用户，在什么场景，通过什么改变，预期出现什么可观察结果”。支持它所需的支撑假设单独标注，不扩大成多个并行主目标。

选择验证方式时考察证明力：原型可验证理解与操作，人工辅助可较快验证价值交付，但不能自动证明自动化性能和规模成本；小范围真实使用可观察行为；对照实验在需要归因且条件允许时采用。明确验证方式能证明什么、仍不能证明什么。

## 2. 候选需求筛选

按“需求→用户问题或必要依赖→假设关系→删除后影响→取舍”推导，避免先列一大批功能再机械打分。

- 必须做：缺少它便无法交付本次核心价值、验证主要假设、观测结果或满足关键约束。纳入后明确最小实现程度。
- 明确不做：本版排除，说明与主要假设无关、成本超限、证据不足、存在负面影响等具体原因。不能只写“非 P0”。
- 以后再说：有潜在价值但本次不必需，写出重启条件，例如前置假设通过、需求证据增加或依赖可用。避免无依据地承诺下一个版本。

价值判断结合痛点强度、发生频率、证据可信度、对假设的贡献。成本判断包括开发、集成、数据准备、推理、评估、运营和人工处理；未知估算说明依据与不确定性，不虚构人天。高价值高成本项如属流程必需，可尝试降低实现范围或验证替代方式，不能仅按象限直接删除。

Kano 分类可帮助识别缺少就无法使用的基本能力、持续改善体验的能力、意外增益与无感或负面能力。分类依赖用户及场景，不能凭名称断定；缺少依据时注明暂定分类，必要时省略。

### 已有产品：从漏斗断点推导范围

1. 先定义用户要完成的任务与最终结果，按真实路径列出可观察环节。付费场景先澄清用户购买的价值，再明确收费对象和计费单位、成本消耗单位及二者关系；不能因模型按量计费就假定用户必须按同样单位购买。
2. 检查各环节是否使用同一用户群、时间窗、去重规则和事件定义。口径不一致、跨期或路径非顺序的数据不能直接拼成转化漏斗；缺失数据标明缺失，不反推成事实。
3. 对可比数据同时考察绝对流失与相邻环节转化，结合访谈、行为或实验判断可能原因。漏斗显示“在哪里掉”，通常不能单独证明“为什么掉”。无基线时把断点作为待验证假设，可先纳入最小观测，不虚构用户量。
4. 比较阻塞影响、证据可信度、上下游依赖及修复成本，优先处理使核心价值无法被触达或获得的瓶颈。多个断点可服务同一主要假设，但每个 P0 仍需独立通过删除检验；不能因为某个专题重要就把专题下全部功能纳入。
5. 先按需列“改进方向／断点证据／拟解决问题／优先级及理由”的简表，再拆到逐功能范围表。专题归类不能替代功能边界与验收。

## 3. 必须做范围表

每行描述一个可验收的能力或动作，避免“智能化”“提升体验”等空泛功能名，避免把多个可独立取舍的功能塞进同一行。

| 功能 | 优先级 | 解决的问题 | 为什么现在做 | 验收标准 |
| --- | --- | --- | --- | --- |

这里是空结构，不将业务示例固化到 Skill。实际使用时填写本次项目的内容。

范围部分先列“明确不做及理由”，将本版边界置于功能清单之前。执行前提与核心假设放在开头；前提描述验证成立所需条件，不能把尚未证实的核心结论当作前提。

“为什么现在做”应体现对假设、核心流程或关键依赖的必要性，已有产品可关联断点证据。“验收标准”说明输入或前置条件、可观察行为和结果、质量要求及关键失败处理。对每行检查适用的异常与兜底：触发条件、是否停止输出或执行、提示和恢复方式、谁接管。无特殊异常时沿用适用的共用规则并引用，不机械增加人工流程。

按需增加：
- 范围边界：支持与不支持的用户、场景、输入、输出及实现深度。
- 必要依赖：前置数据、权限、系统或能力，以及未就绪时的处理。
- 假设关联：关联主要假设或支撑假设；共用编号即可，避免重复长文。
- 成本或约束：有依据的估算及硬限制，未知项标注待确认。

## 4. AI 产品的必要约束

根据当前场景选择检查项，不强制增加全部列或功能：

| 判断项 | 应明确的内容 |
| --- | --- |
| 数据与输入 | 数据来源及可用性、代表性、允许范围、权限或隐私约束（若相关） |
| 输出质量 | 用户任务对应的质量定义、评估方式、代表性测试数据；不能仅写“准确率高” |
| 效率与成本 | 可接受的响应时间、单位任务成本及并发约束；未知值标注待验证 |
| 失败与兜底 | 无法完成、低置信度、错误或超时如何被发现与处理；是否需要人工介入 |
| 最小观测 | 如何知道任务成功、用户如何纠错，以及用何种记录支持效果判断 |

不要默认指定模型、RAG、微调或 Agent 架构；仅在这些选择直接影响范围可行性时讨论。人工辅助需明确边界和消耗，不能把人工贡献当作 AI 自动化效果。不能用降低关键质量、取消纠错或隐藏失败来制造“最小”范围。

证据不足、低置信度或输入超出支持范围时，明确澄清、拒绝、重试或人工处理的条件，不能输出伪确定结论。涉及资金等高影响操作时根据授权、错误后果及现有业务控制确定人工复核或接管边界；不能从单一案例推导所有涉钱场景必须转人工的通用规则。质量与性能门槛须说明样本、评估方法及统计口径，若使用 P90 等分位数，要说明计时起止与失败任务处理。

## 5. 假设验证计划

交付验收通过不等于项目假设成立。来源示例中的转化门槛属于业务验证结果，不能单独用来证明界面或功能交付合格；保留功能行为验收，并将业务门槛单列为效果验证。为主要假设写明：
- 主要指标与必要约束指标，各自的计算口径和基线（如有）。
- 验证对象、招募或样本选择方式、观察时间窗、采集方法。
- 支持假设、需要调整、否定假设或证据不足的判断条件。
- 继续、调整、停止或补充验证的后续决策。

阈值来自已有基线、用户目标、约束或明确的推导。没有依据时给出可讨论的建议并写明依据与待确认状态，不编造行业标准。样本不足、观察不足或数据质量不足时判为证据不足，不机械宣称通过或失败。增长场景需考虑归因与其他变化的干扰；用户满意度与意向不能直接替代真实使用或付款证据。

## 6. 范围可行性与条件推进

在已有证据基础上检查用户是否获得价值或愿意购买、成本收益是否具备可行性、实现是否超出资源限制。AI 能力再问：是否需要 AI 或更简单的方法即可完成；质量应到什么程度；错误由谁处理；数据是否可用及成本如何计算。没有证据的部分写为待验证，不宣称公司一定盈利或用户一定付费。

需要给出范围建议时可采用“建议推进／暂不推进／有条件推进”，明确是建议，不冒充已有立项审批。有条件推进须列出现在可做的最小子集、前置条件、负责确认的角色或待指派项、继续投入的证据门槛，以及未满足时暂停、缩减或重做验证的处理。只有当前范围需要此决策时才输出，不强制新增完整立项章节。

## 7. 交付前质量检查

- 所有 P0 是否能说明删除后对主要假设、流程、观测或硬约束的实质影响？是否存在“便宜就加”“所有功能都是 P0”？
- 用户能否从起点走到可用结果？必要的纠错、兜底和反馈是否缺失？
- 每项是否关联真实问题或必要依赖？证据与建议是否清楚区分？
- 范围与不做事项是否具体？以后再说是否有重新评估条件？
- 功能验收是否可检查，项目验证是否可测量？二者是否混淆？
- 资源、成本、数据、质量和时延是否存在未解决的可行性冲突？关键缺口是否已询问，非关键未知是否明确保留？
- 原型或人工验证是否被误写为完整产品或自动化性能验证？
- 漏斗是否可比，断点原因是否有依据？专题是否已拆成可取舍、可验收功能？
- 执行前提是否与待证假设区分？异常兜底是否明确到适用功能？数字门槛是否有依据与测量口径？
- 条件推进是否明确解锁门槛与失败处理，而非模糊承诺？
- 是否越界扩展成完整研究、立项报告、路线图或 PRD？

## 方法来源与沉淀边界

用户提供的课件 https://w3d2-3-requirements-initiation.vercel.app/ 及方法摘要 https://my.feishu.cn/wiki/REy2wEfxSiVWhAkj9pLc7PpLnOh 提供了“写假设、只留必需、定通过标准”、范围取舍与核心字段。两个材料的 Kano 类别描述存在差异，因此本 Skill 将 Kano 作为按用户场景选用的辅助方法，不固化互相矛盾的分类要求。

用户确认的扩展包括：按输入完整度访谈、一个主要假设及必要支撑假设、比较低成本验证方式、区分交付验收与假设验证、按需检查 AI 约束，以及内容确认后默认交付 HTML。保留方法出处供追溯，Skill 日常使用不依赖重新访问源链接。仅保存通用方法、标准流程、限制和边界，不保存来源中的具体业务案例或本次任务数据。

本次从同一飞书示例补充的通用方法包括：漏斗诊断与功能取舍的衔接、执行前提、不做事项前置、逐功能异常兜底、可测门槛和有条件推进。示例中的业务名称、功能组合、流量、性能阈值及商业结论均不沉淀；对漏斗因果、验收与效果验证、人工接管的适用边界作了区分。
