# MVP 范围表

目标是形成有依据、可执行、可验证的范围决策。每一条纳入项都应连回用户问题、主要假设或完成验证必需的依赖；最小范围仍须支持完整可用流程。沉淀通用方法，不将本次项目的业务名称、功能清单、指标数字、用户画像或经验结论回写到 Skill。

## 先梳理，再制作

1. 阅读用户已提供的材料，识别任务属于新产品、新功能、改版还是增长实验，以及输入属于想法、已有研究还是需求池。区分已确认事实、用户判断、模型建议和待验证假设。链接无法访问时说明缺失的具体内容，不能声称已读；先处理不依赖缺失材料的部分。
2. 从材料中提取目标用户及场景、未解决的问题与证据、当前替代办法、项目目标、候选需求、时间与资源约束。已有产品的改版或增长实验，还需提取当前行为路径、可比的漏斗基线及断点证据；涉及付费时澄清用户购买的价值、计费单位与成本单位，不能默认三者相同。已有信息不重复询问；模糊想法先补问题定义，已有材料检验关键缺口，已有需求池追溯需求与证据并筛选范围。
3. 分轮询问真正影响范围决策的少量问题，通常每轮 1–3 个。问题要有清晰选项，把推荐项置前并标记“推荐”，简述推荐依据；允许用户自由补充或说不确定。优先使用可用的选项弹窗工具。弹窗发出后等待答复，不立即发送 final 或用连续对话挤走弹窗，不把超时或默认选项当作用户回答。等待工具单次不超过 60 秒；未回复时保持关键问题待答。工具不可用时在对话中提出简短选择题。
4. 必须弄清目标用户与场景、核心问题、一个主要验证假设、可用流程、关键约束与验证方向。成本、效果或指标未知时提供有依据的建议并标注待验证，不能编造；缺口若会改变范围取舍，继续询问，非关键缺口可进入待验证项。
5. 汇总“用户与问题、任务场景、主要假设、验证方式、最小流程、硬约束、重要未知项、交付形式”，请用户确认理解。得到确认后制作范围表。用户已明确确认且未发生实质变化时不重复确认；若核心用户、问题、假设或硬约束变化，回到相关问题并更新确认。

只补清影响 MVP 的关键问题。需要完整调研、竞品分析、立项论证或详细 PRD 时说明哪些输入缺失，不在当前任务中自动扩展为这些交付物。

## 决定最小范围

制作或评审范围表时读取 [范围判断与交付标准](references/scope-standard.md)。

- 每版聚焦一个主要假设，可列验证它所必需的支撑假设。多个同等重要目标竞争时，协助用户排序或拆成独立实验。
- 先比较原型、人工辅助、小范围实验和开发产品的验证方式。选择能检验该假设且成本合理的方式；不能用只能证明兴趣的展示替代真实效果、留存或付费验证。
- 对已有产品优先从可比的漏斗和任务路径定位阻塞，区分数据观察与原因假设，再按影响、依赖及验证成本决定先后。不能只凭流失人数最大就断定优先级或原因；具体方法见参考文件。
- 写出从输入、处理、结果交付到必要反馈的最小流程。仅保留使流程可用、假设可测以及关键风险可控的能力，包含必要的观测与反馈手段。
- 对候选需求做删除检验：删去后能否仍验证主要假设、完成流程并满足硬约束？如果能，通常不应作为 P0。依赖项即使用户不可见，也可因验证必需而纳入。
- Kano 与用户价值×成本是辅助判断工具。没有调查依据时分类仅为暂定判断；不强制凑齐类别、虚构评分、增加兴奋型功能，或因成本低就顺手纳入。参考材料存在分类差异时说明采用的定义，不混用标签。
- P0 表示本次验证必需，不表示“重要”“老板想要”或“技术先进”。明确分别列出必须做、明确不做、以后再说；每个排除项写理由，后续项写重新评估条件。
- 对 AI 能力检查所需数据、质量衡量、时延与单位成本、错误处理与必要的人工兜底。只纳入会影响本次取舍和验收的约束，不能套入一整套与当前场景无关的技术方案。

## 输出与确认

先在对话中提供内容草稿。开头简述执行前提与可证伪的主要假设；范围部分先单列“明确不做及理由”，再给出最小可用流程与必须做范围表，随后列以后再说及重启条件、假设验证计划和待验证项。按需附漏斗依据与 AI 约束，不把简单范围表扩写成完整报告。

范围表保留核心列“功能／优先级／解决的问题／为什么现在做／验收标准”。按需增加范围边界、必要依赖、假设关联或成本判断；宽表难读时把扩展信息放到配套小表中。每个功能检查适用的异常与兜底，在验收单元格或关联小表中说明触发条件、系统响应和人工接管边界，不用统一的“失败转人工”代替设计。不要为填列而编造信息。

严格区分两类标准：
- 交付验收：能力做到什么程度算完成，须可观察、可检查；质量和性能要求在有依据时写成数字门槛并附测量口径，不能复制示例阈值。
- 假设验证：用户或业务结果达到什么条件，才能支持继续、调整或停止，须定义指标口径、对象、时间窗与数据来源。

先检查用户价值、成本与收益的可行性以及实现难度；AI 功能再检查使用 AI 的必要性、质量门槛、兜底责任、数据与成本。仅形成当前范围的建议，不替代正式立项审批；有条件推进须写明先做部分、解锁条件与未通过的处理。

先执行参考文件中的质量检查，修复无依据的 P0、断裂流程、模糊边界、无法测量的验收及验证标准。向用户展示需要决策的剩余问题。内容确认后默认生成独立 HTML 文件，除非用户指定其他格式；用户要求直接生成时以该指令为准。HTML 使用中文、清晰分区、可读表格、状态标记、适配窄屏的布局和打印样式，不依赖远程资源。保存到当前任务可写目录，检查内容与文件可用性，有可用浏览器时检查渲染，再提供可点击文件链接或打开预览。

修改既有范围表时沿用已确认的目标与约束，说明新增、移除或调整项的依据，检查对假设、流程、依赖和验证口径的影响。不能在更新中悄悄把待验证建议改为事实。
